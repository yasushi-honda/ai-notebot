# ADR: GitHub Actions の schedule 発火不安定性への対策

- 日付: 2026-09-14
- 状態: 確定（部分対応。恒久解決には至っていない）

## Context

2026-09-14、当日分のAIトレンド記事・介護版記事が09:07 JST（daily.ymlのcron予定時刻）を過ぎても
生成されていないことが発覚した。調査の結果、以下が判明した。

過去の`daily.yml`実行履歴（`gh api .../actions/workflows/daily.yml/runs`）を確認したところ、
`event=schedule`による実行は過去38回中わずか3回のみで、いずれも予定時刻から1時間47分〜2時間28分
遅延していた。2026-09-14分に至っては、cronの予定時刻（00:07 UTC）から1時間以上経過しても
run自体が作成されていなかった。

`daily.yml`のcron設定はプロジェクト開始（2026-09-09）以降に3回変更されており
（`'30 21 * * *'` → `'0 0 * * *'` → `'7 0 * * *'`）、現行cronでの観測機会は本ADR執筆時点で
実質1回のみだった。過去の遅延データの一部は変更前の別cron設定に対するものであり、
単純に「現行cronが5日連続で失敗した」とは言えない。ただし、cron設定によらず一貫して
1.5〜2.5時間規模の遅延が観測されている点は無視できない。

セカンドオピニオンとして`codex`に相談した結果、以下が確認された:

- GitHub公式は、scheduleイベントが高負荷時に遅延・ドロップされうることを明記しており、
  配送保証や上限時間は示していない（[schedule event仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)、
  [troubleshooting](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows)）。
- 2026-09-13分の実行（`event=schedule`、head_sha=`d513393`）は、cron設定変更のコミット
  （`d513393`、2026-09-13T02:11:21Z）のわずか27秒後に発火しており、defaultブランチへの
  新規commitが停滞していたscheduleの詰まりを解消した可能性を示唆する
  （WebSearchで確認した一般的な報告と整合する）。ただし他の2件の遅延実行にはこの相関が
  弱く、確定的な原因特定には至らなかった。
- `daily-digest` concurrency group自体は「scheduleが発火しない」問題の直接原因ではない
  （runが作られた後の待機・キャンセルには影響しうるが、今回の症状はrunが作られる前の
  配送段階の問題）。

## Decision

### 実施した対策（本ADRの範囲）

1. **cronを1日3回に増やす**: `daily.yml`のcronを `'7 0 * * *'` から `'7 21,0,3 * * *'`
   （21:07 UTC＝翌日06:07 JST / 00:07 UTC＝09:07 JST / 03:07 UTC＝12:07 JST）に変更した。
   初版では2回（00:07 / 03:07 UTC）のみだったが、「配送の独立した試行機会を増やすほど
   その日のうちに1回も成功しない確率は下がる」という判断から、decision-makerの提案で
   06:07 JSTにも1回追加した。21:07 UTCはUTC暦日としては前日になるが、JSTでは翌日06:07
   になるため、00:07/03:07 UTCの発火と同じJST日を対象にできる（`Skip if already
   generated`のJST日付判定と整合する）。3回とも「配送が失敗しやすい毎時00分」を
   避けている。
2. **冪等性ガードを追加**: `daily.yml`に「本日分の記事が既に存在するか」を確認する
   ステップ（`Skip if already generated`）を追加し、既に存在する場合は収集・生成・
   出典検証・画像生成の各ステップをスキップする。コミット・サイトのビルド・デプロイは
   `if`条件を付けず常に実行する（`git add`後に`git diff --cached --quiet`で変更の
   有無を見て自動的にno-opになる既存の設計に委ねているため。既存コンテンツでの
   再ビルドは無害かつ、他の要因での反映漏れに対する保険にもなる）。これにより、
   2回のcronが両方成功しても記事が二重生成されたりLLM呼び出しが無駄に倍増したり
   しない（pr-review-toolkitのレビューで「コミットステップにもif条件がある」と
   誤読しうる記述だと指摘・修正）。
   AIトレンド版（`posts`）と介護版（`care`）の存在チェックは別々に行う。
   `build-care.mjs`は失敗しても常にexit 0を返す設計（本体の生成・公開を止めない
   フェイルセーフ）のため、1回目でposts成功・care失敗というケースがあり得る。
   両方まとめて「postsがあるか」だけで判定すると、2回目でcareのリトライ機会が
   永久に失われてしまう（`codex review`で指摘・修正）。
   このガードは`event_name == 'schedule'`（保険の2回目実行）にのみ適用し、
   `workflow_dispatch`（手動実行）では既存記事があっても常にフル実行する。
   このプロジェクトは既存記事の作り直しや障害復旧のために頻繁に手動再実行してきた
   実績があり、ガードを一律適用すると「既存記事があると手動再実行が何もしない
   （サイトの再ビルド・再デプロイだけで終わる）」という回帰を招くところだった
   （`codex review`で指摘・修正）。
3. 今回の欠落分は`gh workflow run daily.yml`で手動リカバリした。

### 見送った対策（今後の検討事項）

- **外部スケジューラへの移行**（GCP Cloud Scheduler → Cloud Run/Functions →
  GitHub API `workflow_dispatch`）: GitHub Actions自体の配送不安定性を構造的に
  回避できる最も堅牢な案だが、新規GCPリソース・認証設計（GitHub App installation
  tokenの短命発行等）が必要で、本プロジェクトの運用規模に対して過剰投資と判断し
  今回は見送った。「毎日必ず特定時刻に公開する」ことが強い要件になった場合は
  再検討する。
- **外部監視・通知**: 一定時刻を過ぎても記事が存在しない場合にIssue等で通知する仕組み。
  監視自体をGitHub Actionsのscheduleに置くと同時に機能しなくなるリスクがあるため、
  外部（Cloud Scheduler等）で動かす必要があり、これも上記の外部スケジューラ案と
  合わせて検討する方が合理的なため今回は見送った。
- **`push`を補助トリガーにする案**: ほぼ毎日コミットがある本プロジェクトでは自然な
  回復策になりうるが、コミットがない日には効かず、根本対策にはならないため採用しなかった。

## Rationale

- 1日2回のcron + 冪等性ガードは、既存のworkflowファイル1つの変更で完結し、新規の
  外部インフラ・認証情報を必要としない、コストの低い緩和策である。「2回とも配送が
  失敗する」確率は「1回失敗する」確率よりも大幅に低いと期待でき、費用対効果が高い。
- `weekly.yml`（週1回、日曜11:07 JST）には同様の複数cron化を適用しなかった。週次は
  `weeklyWindow()`が「公開日」を起点に対象週を計算するため、2回目のcronが翌日にずれると
  対象週の開始日（weekStart）も変わってしまい、`docs/adr/adr-2026-09-14-weekly-digest.md`
  で対処した「週は日曜始まり」という前提が別の形で壊れるリスクがある。週次の配送信頼性
  向上は、日次側の対策の効果を見てから改めて検討する。

## Consequences

- CI実行コストが1日あたり最大3回分（最初の1回が成功すれば残りは軽量スキップ実行になり
  実質1回分強）に増える。
  publicリポジトリのためActions分数の課金上限には影響しない。
- 依然としてGitHub側の配送が2回とも失敗・大幅遅延するケースには対応できない
  （根本解決ではなく緩和策）。この頻度が今後も高いようであれば、外部スケジューラへの
  移行を再検討する。
- `weekly.yml`の配送信頼性は本ADRの対策範囲外のまま。次に同種の問題が週次側で
  顕在化した場合、本ADRの「見送った対策」を再検討すること。
