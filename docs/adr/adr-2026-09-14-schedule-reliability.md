# ADR: GitHub Actions の schedule 発火不安定性への対策

- 日付: 2026-09-14
- 状態: 確定（部分対応。恒久解決には至っていない）

## Context

2026-09-14、当日分のAIトレンド記事・介護版記事が09:07 JST（daily.ymlのcron予定時刻）を過ぎても
生成されていないことが発覚した。調査の結果、以下が判明した。

過去の`daily.yml`実行履歴（`gh api .../actions/workflows/daily.yml/runs`）を確認したところ、
`event=schedule`による実行は過去38回中わずか3回のみで、いずれも予定時刻から1時間47分〜2時間28分
遅延していた。2026-09-14分に至っては、cronの予定時刻（00:07 UTC）から1時間以上経過しても
run自体が作成されていなかった。

`daily.yml`のcron設定はプロジェクト開始（2026-09-09）以降に3回変更されており
（`'30 21 * * *'` → `'0 0 * * *'` → `'7 0 * * *'`）、現行cronでの観測機会は本ADR執筆時点で
実質1回のみだった。過去の遅延データの一部は変更前の別cron設定に対するものであり、
単純に「現行cronが5日連続で失敗した」とは言えない。ただし、cron設定によらず一貫して
1.5〜2.5時間規模の遅延が観測されている点は無視できない。

セカンドオピニオンとして`codex`に相談した結果、以下が確認された:

- GitHub公式は、scheduleイベントが高負荷時に遅延・ドロップされうることを明記しており、
  配送保証や上限時間は示していない（[schedule event仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)、
  [troubleshooting](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows)）。
- 2026-09-13分の実行（`event=schedule`、head_sha=`d513393`）は、cron設定変更のコミット
  （`d513393`、2026-09-13T02:11:21Z）のわずか27秒後に発火しており、defaultブランチへの
  新規commitが停滞していたscheduleの詰まりを解消した可能性を示唆する
  （WebSearchで確認した一般的な報告と整合する）。ただし他の2件の遅延実行にはこの相関が
  弱く、確定的な原因特定には至らなかった。
- `daily-digest` concurrency group自体は「scheduleが発火しない」問題の直接原因ではない
  （runが作られた後の待機・キャンセルには影響しうるが、今回の症状はrunが作られる前の
  配送段階の問題）。

## Decision

### 実施した対策（本ADRの範囲）

1. **cronを1日3回に増やす**: `daily.yml`のcronを `'7 0 * * *'` から `'7 21,0,3 * * *'`
   （21:07 UTC＝翌日06:07 JST / 00:07 UTC＝09:07 JST / 03:07 UTC＝12:07 JST）に変更した。
   初版では2回（00:07 / 03:07 UTC）のみだったが、「配送の独立した試行機会を増やすほど
   その日のうちに1回も成功しない確率は下がる」という判断から、decision-makerの提案で
   06:07 JSTにも1回追加した。21:07 UTCはUTC暦日としては前日になるが、JSTでは翌日06:07
   になるため、00:07/03:07 UTCの発火と同じJST日を対象にできる（`Skip if already
   generated`のJST日付判定と整合する）。3回とも「配送が失敗しやすい毎時00分」を
   避けている。
2. **冪等性ガードを追加**: `daily.yml`に「本日分の記事が既に存在するか」を確認する
   ステップ（`Skip if already generated`）を追加し、既に存在する場合は収集・生成・
   出典検証・画像生成の各ステップをスキップする。コミット・サイトのビルド・デプロイは
   `if`条件を付けず常に実行する（`git add`後に`git diff --cached --quiet`で変更の
   有無を見て自動的にno-opになる既存の設計に委ねているため。既存コンテンツでの
   再ビルドは無害かつ、他の要因での反映漏れに対する保険にもなる）。これにより、
   2回のcronが両方成功しても記事が二重生成されたりLLM呼び出しが無駄に倍増したり
   しない（pr-review-toolkitのレビューで「コミットステップにもif条件がある」と
   誤読しうる記述だと指摘・修正）。
   AIトレンド版（`posts`）と介護版（`care`）の存在チェックは別々に行う。
   `build-care.mjs`は失敗しても常にexit 0を返す設計（本体の生成・公開を止めない
   フェイルセーフ）のため、1回目でposts成功・care失敗というケースがあり得る。
   両方まとめて「postsがあるか」だけで判定すると、2回目でcareのリトライ機会が
   永久に失われてしまう（`codex review`で指摘・修正）。
   このガードは`event_name == 'schedule'`（保険の2回目実行）にのみ適用し、
   `workflow_dispatch`（手動実行）では既存記事があっても常にフル実行する。
   このプロジェクトは既存記事の作り直しや障害復旧のために頻繁に手動再実行してきた
   実績があり、ガードを一律適用すると「既存記事があると手動再実行が何もしない
   （サイトの再ビルド・再デプロイだけで終わる）」という回帰を招くところだった
   （`codex review`で指摘・修正）。
3. 今回の欠落分は`gh workflow run daily.yml`で手動リカバリした。

### 見送った対策（今後の検討事項）

- **外部スケジューラへの移行**（GCP Cloud Scheduler → Cloud Run/Functions →
  GitHub API `workflow_dispatch`）: GitHub Actions自体の配送不安定性を構造的に
  回避できる最も堅牢な案だが、新規GCPリソース・認証設計（GitHub App installation
  tokenの短命発行等）が必要で、本プロジェクトの運用規模に対して過剰投資と判断し
  今回は見送った。「毎日必ず特定時刻に公開する」ことが強い要件になった場合は
  再検討する。
- **外部監視・通知**: 一定時刻を過ぎても記事が存在しない場合にIssue等で通知する仕組み。
  監視自体をGitHub Actionsのscheduleに置くと同時に機能しなくなるリスクがあるため、
  外部（Cloud Scheduler等）で動かす必要があり、これも上記の外部スケジューラ案と
  合わせて検討する方が合理的なため今回は見送った。
- **`push`を補助トリガーにする案**: ほぼ毎日コミットがある本プロジェクトでは自然な
  回復策になりうるが、コミットがない日には効かず、根本対策にはならないため採用しなかった。

## Rationale

- 1日2回のcron + 冪等性ガードは、既存のworkflowファイル1つの変更で完結し、新規の
  外部インフラ・認証情報を必要としない、コストの低い緩和策である。「2回とも配送が
  失敗する」確率は「1回失敗する」確率よりも大幅に低いと期待でき、費用対効果が高い。
- `weekly.yml`（週1回、日曜11:07 JST）には同様の複数cron化を適用しなかった。週次は
  `weeklyWindow()`が「公開日」を起点に対象週を計算するため、2回目のcronが翌日にずれると
  対象週の開始日（weekStart）も変わってしまい、`docs/adr/adr-2026-09-14-weekly-digest.md`
  で対処した「週は日曜始まり」という前提が別の形で壊れるリスクがある。週次の配送信頼性
  向上は、日次側の対策の効果を見てから改めて検討する。

## Consequences

- CI実行コストが1日あたり最大3回分（最初の1回が成功すれば残りは軽量スキップ実行になり
  実質1回分強）に増える。
  publicリポジトリのためActions分数の課金上限には影響しない。
- 依然としてGitHub側の配送が2回とも失敗・大幅遅延するケースには対応できない
  （根本解決ではなく緩和策）。この頻度が今後も高いようであれば、外部スケジューラへの
  移行を再検討する。
- `weekly.yml`の配送信頼性は本ADRの対策範囲外のまま。次に同種の問題が週次側で
  顕在化した場合、本ADRの「見送った対策」を再検討すること。

## Amendment（2026-09-27）: weekly.ymlにも複数cronを適用

decision-makerから「11:07 JST単発では、配送遅延時に11時を過ぎてしまい遅すぎる」との
指摘を受け、`weekly.yml`にも複数cron化を適用した。

### 本ADR初版で見送った理由との整合

初版の「Rationale」では、週次への複数cron化を見送った理由を「2回目のcronが翌日に
ずれると`weeklyWindow()`の`weekStart`（週は日曜始まり）が変わってしまう」としていた。
今回はこの懸念に対し、**リトライを翌日ではなく同じ日曜の午前中に collapse させる**
ことで対処した。

- 変更後のcron: `30 23 * * 6`（JST日曜08:30） / `30 0 * * 0`（JST日曜09:30） /
  `30 1 * * 0`（JST日曜10:30）。いずれも同一のJST暦日（日曜）に収まる。
- daily.ymlの3回cron（06:07/09:07/12:07 JST、実質12時間規模に分散）と異なり、
  週次は「11時までに終わらせる」という運用要件が主目的のため、間隔を2時間規模に詰めた
  （初版のRationaleが懸念していた「日をまたぐドリフト」は、間隔を詰めたことで構造的に
  発生しなくなった）。
- `Skip if already generated`ガード（daily.ymlと同じ設計）を追加し、`weekStart`の
  ファイル存在チェックで二重生成・LLM呼び出しの無駄な重複を防いでいる。
  `event_name == 'schedule'`のみに適用し、`workflow_dispatch`は常にフル実行する
  （既存の手動リカバリ運用を止めないため）。

### 検討したが却下した対策: concurrencyグループの分離

初回の`codex review`で、間隔の詰まった週次3cronを`daily.yml`と同じ`daily-digest`
concurrencyグループに残すと、GitHub Actionsの「同一グループでpending中のrunは、
新しいrunがキューイングされると自動キャンセルされる」仕様により、週次retry同士だけ
でなく`daily.yml`の09:07 JSTリカバリrunまで退避（evict）させてしまうリスクを指摘された。

これを受けて一度`weekly.yml`のconcurrencyグループを独立した`weekly-digest`に分離する
修正を実施したが、**最終確認の2回目`codex review`で、分離によって生じる別の欠陥2件
（いずれもP1相当）が発覚し、この対策自体を撤回した**:

1. `weekly.yml`が独立グループになると`daily.yml`/`care-rebuild.yml`と真に並行実行され
   うる。`weekly.yml`側にはpush失敗時のfetch+rebase+再pushループを追加したが、
   `daily.yml`/`care-rebuild.yml`側は単純な`git push`のままのため、**weeklyのpushが
   先に成功した場合はdaily/care側が非fast-forwardで失敗し、その日の本体記事
   （日次記事・介護版）がcommitもdeployもされなくなる**。今回のリトライは片方向
   （weeklyが負けた場合）にしか対応しておらず、非対称だった。
2. リトライでrebaseに成功しても、`site/dist`は**リベース前の内容でビルド済み**のため、
   並行していた他ワークフローの新しい変更（当日分のposts/care）を含まない。この状態で
   Pages artifactをアップロード・デプロイすると、既に反映されているはずの新しい
   コンテンツを古い成果物で上書きしてしまう。

「週次のリトライ機会を増やす」という当初の目的に対し、分離案は**本体パイプライン
（日次記事・介護版）の信頼性を損なう**という、解決したい問題より深刻な回帰を生む
ものだった。そのため`git revert`でconcurrencyグループの分離を取り消し、`daily-digest`
共有グループに戻した（本Amendmentの本文で説明した設計のまま）。

### 追記（同日）: `queue: max`でpending run退避リスクを解消

上記「残存リスク」（`daily-digest`共有グループでのpending run退避）は、いったん
「許容する」と判断して確定させたが、handoff前の§4.7対症療法判定で必須のWebSearchを
実施した際、**GitHub Actionsが2026-05-07に`concurrency`ブロックへ`queue`オプションを
追加していた**ことが判明した（docs.github.com公式ドキュメントで確認）。

- `queue: single`（デフォルト・従来の唯一の挙動）: 同一グループでpending中のrunは
  1件のみ許可。新しいrunがキューイングされると既存のpending runはキャンセルされる
  （本ADRがこれまで前提にしていた挙動そのもの）。
- `queue: max`: 同一グループで最大100件のrunをキャンセルせず順序通りに逐次処理する。
- 制約: `cancel-in-progress: true`との併用は不可（3ワークフローとも元々`false`のため
  問題なし）。

`daily.yml`・`weekly.yml`・`care-rebuild.yml`の3ワークフロー全てに`queue: max`を追加し、
上記の「残存リスク」を許容ではなく解消する対応に切り替えた。これにより、間隔の詰まった
週次3cronがdaily.ymlの09:07 JSTリカバリrunを退避させるリスクだけでなく、daily.yml
自身の3cron同士が互いを退避させる既存の潜在リスクも同時に解消される。

**ツールの既知ギャップ**: ローカルの`actionlint`（v1.7.12、2026-03-30リリース）は
`queue`キーを未知のキーとしてエラー扱いする（機能公開日2026-05-07より前のリリースの
ため）。`rhysd/actionlint`のissue #657で同じ既知ギャップとして報告されている。CI
（`ci.yml`）はactionlintを実行していないためブロッカーにはならないが、ローカルでの
構文チェック時にこのfalse positiveが出ることを次回以降のセッションのために記録する。

### 残存リスク

- 3回とも配送が失敗・大幅遅延した場合は依然として救済されない（`queue: max`は
  「キャンセルされず待たされる」ことは保証するが、そもそも配送されない・runが作られない
  ケースには対応できない。初版と同じ根本的な制約）。この場合は
  `gh workflow run weekly.yml`での手動リカバリに委ねる。
- `queue: max`で複数runが直列に積み上がった場合、後方のrunの実行開始が予定時刻より
  遅れる可能性がある（キャンセルされるより望ましいトレードオフと判断）。各runの
  実行時間は短く（daily.yml・weekly.ymlとも実測で数十秒〜数分規模）、`Skip if already
  generated`ガードにより既に成功済みのrunは即座にno-opで終わるため、積み上がりが
  長時間化するリスクは低いと見積もる。実際の発火実績は次回の`/config-review`等で
  確認する。

### 追記（2026-09-28）: 3回cronの中間枠が一度も発火せず、2回cronへ縮小

上記「実際の発火実績」の確認（Issue #50調査中に実施）で、`daily.yml`の3回cron
（21:07/00:07/03:07 UTC）のうち**中間の00:07 UTC枠が直近15日以上の実行履歴で
一度も発火した形跡がない**ことが判明した（`gh run list --workflow=daily.yml`の
`createdAt`を日次で確認。21:07 UTC枠は毎回2.4〜2.8時間遅延して23:3x〜23:5x UTCに
着地しており、これが00:07 UTCの発火時刻とほぼ重なっていたことと一致）。

GitHub Community（[Discussion #55127](https://github.com/orgs/community/discussions/55127)）
では、同一cron式が文字通り同時刻に重複する場合に片方が無警告でスキップされる
未文書化の挙動が報告されている。今回の事象は文字通りの同時刻重複ではなく「配送遅延が
積み重なった結果、実質的に時刻が接近した」ケースだが、同種の未文書化挙動が働いている
可能性が高いと判断した。GitHub公式の一次ソースでこの具体的な因果関係を確定できたわけ
ではなく、**根本原因は状況証拠に基づく仮説（確度は高いが未確定）** であることを明記する。

対策として、当初は3時間間隔を4時間間隔に広げる案（19:07/23:07/03:07 UTC）を実装したが、
`codex review`で**新しい23:07 UTC枠がweekly.ymlの日曜最初の実行（23:30 UTC）のわずか
23分前になり、共有する`daily-digest` concurrencyグループ（`queue: max`）により週次の
保険実行を待たせ、「11時JST締切」要件を壊しかねない**と指摘された（P2）。

直近15日以上の実行履歴では21:07 UTC・03:07 UTCの2枠はどちらも一度も欠落したことが
なく（欠落していたのは中間枠だけ）、3枠目を無理に安全な時間帯へ押し込むより中間枠
自体を廃止する方が、週次との新たな衝突リスクを増やさず現状の信頼性（実質2/2枠が
常に成功）を維持できると判断し、`'7 21,0,3 * * *'`から`'7 21,3 * * *'`（06:07/12:07 JST
の2回）に変更した（PR #51）。

**今後の監視事項**: 新しい2回cronが実際に安定して2/2発火し続けるかは、次回以降の
`/config-review`または本ADRの追記で確認する。もし将来的にどちらかの枠が欠落し
始めた場合、今回の根本原因仮説（配送遅延の積み重ねによる実質的な時刻衝突）が
誤りである可能性を再検討する必要がある。

## Amendment（2026-10-06）: 外部スケジューラ案を採用

2026-10-06 に daily.yml の 06:07 JST 枠が約 4 時間たっても発火せず、同種の事象は 7 件目になった
（PR #51 の 2 回 cron 化の後も再発）。本 ADR で「最も堅牢だが投資が重い」として保留していた
外部スケジューラ案を、GCP Cloud Scheduler（+ Cloud Workflows + GitHub App のインストールトークン。秘密鍵は Cloud KMS に署名専用で置く）で採用した。
GitHub の cron は保険として残し、冪等性ガードに `skip_if_exists` 入力を足して併用する。
詳細: `adr-2026-10-06-cloud-scheduler-dispatch.md`。
