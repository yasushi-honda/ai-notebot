## セッション概要

`/catchup`のIssue #50（介護版AIハック生成失敗: 2026-09-28）調査で、daily.ymlの
1日3回cron中1回（00:07 UTC枠）が直近15日以上一度も発火していないことが判明し、
それが#50の原因かと思われたが、実行ログを精査した結果**無関係**と判明。真の原因は
`curate-care.mjs`自身の品質ゲート（全文脚注必須ルール）だった。

### 実装: PR #51「介護版の全文脚注ゲート対応とdaily.ymlのcron間隔拡大」

3つの独立した問題を発見・修正した（すべて同一PR内、codex reviewサイクルで2段階発覚）:

1. **Issue #50の真因**: 「AIが生成した内容を人間が確認する」等、出典に基づかない
   一般的な実務助言文に脚注を付けられず、`curate-care.mjs`の再生成3回を使い切って
   生成失敗していた。プロンプトに「最も近い出典を引用するか、その文自体を書かない」
   ことを明示し、`MAX_REGENERATE_ATTEMPTS`を3→5に拡大。
2. **daily.ymlのcron欠落**（副次的発見、#50とは無関係）: 3回cron中1回（00:07 UTC）が
   一度も発火していなかった。当初4時間間隔化（19:07/23:07/03:07 UTC）で対処したが、
   1回目のcodex reviewで**新しい23:07 UTC枠がweekly.ymlの日曜最初の実行（23:30 UTC）の
   23分前になり、共有concurrencyグループ経由で週次の「11時JST締切」要件を壊しかねない**
   とP2指摘。実績十分（一度も欠落なし）な21:07/03:07 UTCの2枠に絞る形へ再修正して解決
   （詳細・根本原因の未確定性は`docs/adr/adr-2026-09-14-schedule-reliability.md`追記参照）。
3. **workArea誤分類**（2回目=最終確認のcodex reviewで発見）: 直近2記事が「事務・記録」
   「情報共有」を使用済みのため除外する仕組みが、ラベルの選び直しだけを指示しており、
   記事の題材自体は除外対象（事務・記録＝記録要約）のままラベルだけ貼り替えられていた
   （2回連続再発）。「題材自体を許可されたworkAreaに実際に合致するものへ変える」ことを
   明示して修正、再生成でケアプランに実際に合致する内容になったことを確認。

**codex reviewの運用上の注意点（次回への申し送り）**: 2回目レビューの最初の実行試行が
ログ0バイト・セッション未作成のまま「completed」通知が来る現象が発生し、それでも
1ブランチ2回のhookカウンタは消費済み扱いになった。AskUserQuestionでdecision-makerの
承認を得て`CODEX_REVIEW_APPROVED=1`で再実行し直して解決したが、**「completed」通知だけで
実際にレビューが完了したと判断せず、ログ行数・codexセッションファイルの実在を都度確認する
必要がある**（本ハンドオフの後続セッションはこの現象自体の再発有無を観察対象にしてよい）。
